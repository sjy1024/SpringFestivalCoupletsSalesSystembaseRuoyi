# 网络协议学习笔记（结合本项目 + 嵌入式视角）

> 目标读者：正在学 STM32 嵌入式、刚接触 OTA 与 4G 模块的自己
> 参照项目：RuoYi-Vue 春联商城（后端 Spring Boot + 小程序 + AI 服务）

## 一、先回答：项目里用到 Socket 了吗？

**结论：没有手写 Socket 代码，也没有用 WebSocket。但 TCP Socket 无处不在——HTTP、MySQL、Redis 底层全是 TCP 连接，只是被框架封装了，你看不见而已。**

项目实际用到的通信协议清单：

| 协议               | 用在哪                  | 底层        | 项目代码位置                                                      |
| ---------------- | -------------------- | --------- | ----------------------------------------------------------- |
| HTTP（服务端）        | 管理后台/小程序的所有接口        | TCP       | ruoyi-admin 里所有 `@RestController`（如 ClGoodsController）      |
| HTTP（客户端，JDK 原生） | 通用 HTTP 请求工具         | TCP       | `ruoyi-common/.../utils/http/HttpUtils.java`（URLConnection） |
| HTTP（客户端，OkHttp） | 调用 LM Studio 的 AI 接口 | TCP       | `ruoyi-admin/.../service/OpenAiCompatibleLlmService.java`   |
| MySQL 协议         | 数据库读写                | TCP 3306  | application-druid.yml + Druid 连接池                           |
| Redis 协议（RESP）   | 缓存/登录令牌              | TCP 6379  | application.yml 里 spring.redis 配置（Lettuce 客户端）              |
| HTTPS            | 生产环境部署               | TCP + TLS | cl-uniapp/env.config.js 里的 `https://your-domain.com`        |

**类比理解**：Socket 就像墙上的"电话插座"，项目里没有自己装插座（手写 Socket），但打的每通电话（HTTP 请求、SQL 查询）都从插座走。Tomcat（Web 容器）就是帮你接电话的"前台总机"。

## 二、网络分层模型（先看地图，再上路）

TCP/IP 四层模型（嵌入式够用了，不用背 OSI 七层）：

```
┌─────────────────────────────────────────┐
│ 应用层   HTTP / MQTT / DNS / MySQL协议    │  ← 你写的 Controller、AT+HTTP
├─────────────────────────────────────────┤
│ 传输层   TCP / UDP                        │  ← 端口号、三次握手在这层
├─────────────────────────────────────────┤
│ 网络层   IP（IP地址、路由）               │  ← 4G模块/路由器帮你做的
├─────────────────────────────────────────┤
│ 链路层   WiFi 802.11 / 以太网 / 4G LTE    │  ← 硬件和驱动做的事
└─────────────────────────────────────────┘
```

**类比**：寄快递。链路层是"卡车和公路"，网络层是"分拣中心决定走哪条路"，传输层是"快递单号（保证包裹不丢、按序到达）"，应用层是"箱子里装的啥（网页/固件/聊天）"。

**嵌入式视角的巨大优势**：4G 模块（EC200、Air724）和 ESP8266 已经把下面三层全部做好了，你只需要通过 AT 指令操作"应用层"。这就是为什么模块化硬件降低了网络编程门槛。

## 三、TCP vs UDP（嵌入式的两把扳手）

| 特性    | TCP               | UDP          |
| ----- | ----------------- | ------------ |
| 连接    | 先三次握手建立连接         | 不连接，直接发      |
| 可靠性   | 不丢、不乱、不重（确认+重传机制） | 尽力而为，丢了就丢了   |
| 速度/开销 | 慢，头部 20 字节起       | 快，头部固定 8 字节  |
| 类比    | 打电话（先接通再说话）       | 寄明信片（写了就寄）   |
| 典型用途  | HTTP、MQTT、文件传输    | DNS、视频流、心跳上报 |

### 3.1 三次握手（为什么是三次不是两次）

```
客户端 ──SYN──> 服务端      "我想和你通话"
客户端 <──SYN+ACK── 服务端   "可以，我也能听到你吗？"
客户端 ──ACK──> 服务端       "能听到，开始说话"
```

两次不行：服务端无法确认"自己发出去的包客户端收到了没"。本质是**双方都要确认一次自己和对方的收发能力都正常**。

### 3.2 四次挥手（为什么比握手多一次）

因为 TCP 是全双工（双向同时说话），关连接要"两边都同意"：一方说"我说完了"（FIN），另一边回"知道了"（ACK），但它可能还有话没说完，等它也说完了再发 FIN，最后确认。**中间那两步不能合并，因为收到 FIN 的人可能还有数据没发完。**

### 3.3 嵌入式选型经验

- **OTA 下载固件 → TCP**（一个字节都不能错，错了设备变砖）
- **设备心跳/传感器定时上报 → UDP 或 MQTT 都行**（丢一两条无所谓）
- **实时指令下发 → MQTT**（服务器能主动推，HTTP 做不到）

### 3.4 常见坑

1. **TCP 粘包**：连续发两条消息可能被合并成一次收到（TCP 是"字节流"没有消息边界）。解决：定长帧 / 长度前缀 / 分隔符。STM32 串口收 AT 响应同样有这个问题
2. **断线重连**：嵌入式设备必须自己做（4G 信号会断），HTTP 客户端要设超时+重试，参考 OpenAiCompatibleLlmService 里 `connectTimeout(30s) / readTimeout(180s)` 的写法
3. **socketTimeout**：项目里 Druid 连接池就配了这个（DruidProperties.java 第 30 行）——数据库 TCP 连接多久没响应就掐断，防止线程被卡死。含义和串口通信的"超时重发"思想一致

## 四、Socket 到底是什么

**Socket = (IP 地址, 端口号) 这对组合 + 操作系统提供的读写接口。** 它不是协议，是"插座"——编程接口。

```c
/* 服务端流程（伪代码，帮助理解，嵌入式同理） */
socket()    → 买个接线板
bind()      → 绑定到本机 IP:8080 端口
listen()    → 挂出"营业中"牌子
accept()    → 有客户上门，为其生成一条专线（新 socket）
recv/send   → 在专线上读写数据
close()     → 挂断

/* 客户端流程 */
socket()    → 买个电话
connect()   → 拨号到 对方IP:端口
send/recv   → 通话
close()     → 挂断
```

**为什么本项目 Java 代码里看不到这些？** 因为 Tomcat 已经在 `8080` 端口帮你 `bind+listen+accept` 了，每来一个 HTTP 请求就交给一个线程去处理，你只管写"这个请求来了做什么"（Controller）。就像你不需要自己开快递站，只用把包裹交给快递员。

**ESP8266/4G 模块的 AT 指令就是把这个流程翻译成了串口命令**：

```
AT+CIPSTART="TCP","112.74.44.100",8080   ← connect()：建立 TCP 连接
AT+CIPSEND=128                          ← 我要发 128 字节
<数据>
AT+CIPCLOSE                             ← close()：断开
```

## 五、HTTP 协议（本项目的骨架，也是 OTA 的载体）

### 5.1 一次 HTTP 请求的完整报文（背下来这个，HTTP 就懂一半）

```http
POST /system/goods HTTP/1.1          ← 请求行：方法 路径 协议版本
Host: 127.0.0.1:8080                 ← 头部：键值对
Authorization: Bearer eyJhbGciOi...  ← JWT 令牌（鉴权）
Content-Type: application/json       ← 告诉服务器：请求体是 JSON
Content-Length: 46

{"goodsName":"福字","price":9.9}     ← 请求体
```

响应：

```http
HTTP/1.1 200 OK                      ← 状态行：版本 状态码
Content-Type: application/json

{"code":200,"msg":"操作成功"}        ← 响应体
```

**和串口协议对比着记**：这就是一个"文本帧协议"——帧头（请求行）、配置区（Header）、帧体（Body）。你在 STM32 上解析 GPS 的 `$GPRMC,...` 报文，和解析这个是同一回事，只是字段更多。

### 5.2 方法 → 语义（对应 RuoYi 的 CRUD 五件套）

| 方法     | 语义             | ClGoodsController 里的注解                             |
| ------ | -------------- | -------------------------------------------------- |
| GET    | 查询（参数在 URL，幂等） | `@GetMapping("/list")`、`@GetMapping("/{goodsId}")` |
| POST   | 新增（参数在请求体）     | `@PostMapping` → add()                             |
| PUT    | 全量修改           | `@PutMapping` → edit()                             |
| DELETE | 删除             | `@DeleteMapping("/{goodsIds}")` → remove()         |

这就是 **RESTful 风格**：用方法表达"做什么"，用 URL 表达"对谁做"，而不是把动词写进 URL（坏例子：`/addGoods`）。

### 5.3 状态码（记住 5 个够用）

| 码   | 含义                | 项目里对应场景                  |
| --- | ----------------- | ------------------------ |
| 200 | 成功                | 正常返回 AjaxResult          |
| 401 | 未认证（没登录/token 无效） | 小程序 token 过期，跳登录页        |
| 403 | 已认证但无权限           | `@PreAuthorize` 权限字符串对不上 |
| 404 | 资源不存在             | URL 写错                   |
| 500 | 服务器内部错误           | 后端抛异常                    |

### 5.4 项目里的三个 HTTP 客户端（同一个协议，三种封装层次）

1. **HttpUtils.java（JDK URLConnection）**：最原始，手拼 URL 参数，一行行读流。适合理解原理
2. **OpenAiCompatibleLlmService（OkHttp）**：现代客户端，链式配置超时、连接池自动管理
3. **小程序 request.js（wx.request 封装）**：前端侧封装，自动带 token、统一错误处理

**三层封装的共性**：都逃不开 `连接 → 发请求 → 读响应 → 关闭/复用` 这四步，正如串口永远逃不开 `配置波特率 → 收 → 发`。

### 5.5 Keep-Alive 与短连接

HTTP/1.1 默认长连接：一次 TCP 握手后可以发多个 HTTP 请求（省去反复握手）。HttpUtils.java 第 77 行 `connection.setRequestProperty("connection", "Keep-Alive")` 就是在请求这个特性。**嵌入式注意**：ESP8266 用 AT 指令时，一条 TCP 连接发完一个 HTTP 请求就断（短连接），最简单；做 OTA 断点续传时才需要维护长连接。

## 六、DNS：域名 → IP 的"电话簿"

浏览器/设备访问 `your-domain.com` 前先问 DNS 服务器"它的 IP 是多少"。

**嵌入式坑**：4G 模块 AT 指令里通常有专门的域名解析命令（如 `AT+EDNS` 或连接时直接写域名让模块自己解析）。ESP8266 的 `AT+CIPSTART` 也支持直接填域名。开发期直接用 IP（如 `127.0.0.1:8080`）省事，上线再换域名。

***

## 七、鉴权：JWT（JSON Web Token）

项目登录流程：`POST /login` → 服务端生成 token（一串 base64 字符串）→ 之后每个请求带在 `Authorization: Bearer xxx` 头里。

**为什么嵌入式设备也适合这种方案**：

- 无状态：服务器不用记"谁登录过"（token 里自带签名，验签即可），对资源紧张的设备友好
- 一个 HTTP 头就搞定，ESP8266 拼 AT 指令也能带上

**和本项目小程序的关系**：cl-uniapp 的 request.js 统一从本地缓存取 token 塞进 header，401 时跳登录页——这就是你将来 OTA 设备端"注册-拿凭证-带凭证下载"的原型。不过注意：ESP8266 走纯 AT 指令带 JWT 很麻烦，所以设备端接口通常改用"设备号+密钥"或直接匿名+IP 白名单（对应小程序 `app/*` 接口的设备号鉴权思路）。

***

## 八、数据库与 Redis：另一类 TCP 协议

- **MySQL 协议**（端口 3306）：二进制协议，Druid 连接池管理 TCP 连接的创建/复用/超时。DruidProperties 里的 `socketTimeout` 就是 TCP 层的"等响应超时"
- **Redis RESP 协议**（端口 6379）：文本协议，极简，`SET key value\r\n` 这种。RuoYi 用它存登录 token、验证码、字典缓存

**理解要点**：它们和 HTTP 的本质区别是——HTTP 是"请求-响应"的短对话模型（适合广域网、防火墙友好），MySQL/Redis 是"专用热线"模型（局域网内、长连接、低延迟）。连嵌入式里你的设备不会直数据库，一定是走 HTTP/MQTT 找"中间人"（服务器）。

***

## 九、HTTPS/TLS：给 TCP 上锁

生产环境 `https://` = 在 TCP 和 HTTP 之间加一层 TLS 加密。握手时通过证书验证服务器身份，之后所有数据对称加密。

**嵌入式现状**：很多 MCU 的 HTTP 客户端（含 ESP8266 AT 固件）默认不校验证书，存在被中间人攻击的风险，毕设演示无碍，产品要做的话选支持 TLS 的模块（如 Air724/EC200 内置）。**回忆一下**：这和你学的 USART 校验位（奇偶校验查 1 字节错）思想同源，只是 TLS 防"偷看+篡改"，强度是天壤之别。

## 十、嵌入式视角：OTA 与 4G 模块如何用上这些知识

### 10.1 4G 模块的本质

4G 模块 = 调制解调器 + 完整 TCP/IP 协议栈，通过 AT 指令暴露能力。你不需要实现协议，只需要"会点菜"：

```
AT+CGDCONT=1,"IP","cmnet"        ← 配置 APN（相当于插 SIM 卡开通网络）
AT+NETOPEN                       ← 激活网络（拿到 IP，链路层/网络层就绪）
AT+CIPOPEN=0,"TCP","x.x.x.x",8080 ← 传输层：建 TCP 连接
AT+CIPSEND=0,100                 ← 发 100 字节数据（应用层内容由你拼）
```

### 10.2 OTA 完整链路（把前面所有知识串起来）

```
STM32 发起 OTA
  │
  ├─ ① DNS：把服务器域名解析成 IP（模块代劳）
  ├─ ② TCP：三次握手连到服务器 80/8080 端口
  ├─ ③ HTTP：GET /api/ota/check?version=1.0.0 → 返回 JSON（有无新版本）
  ├─ ④ HTTP：GET /api/ota/download → 服务器把固件 bin 按字节流回传
  │      └─ STM32 逐包收到 → 写入 Flash 备份区（解锁→擦页→编程→上锁）
  ├─ ⑤ 校验：算接收数据的 MD5/CRC32，和服务器告知的值比对
  └─ ⑥ 置升级标志 → 重启 → Bootloader 把备份区搬到 App 区 → 跑新固件
```

其中 ①② 全由模块完成，③④⑤⑥ 是你写代码的部分。**对照本项目的角色**：③④ 就相当于小程序的 `request.js` 调 `/system/goods/list`；服务器那头就是将来在 ruoyi-admin 里加的 OTA Controller——和 ClGoodsController 结构一模一样。

### 10.3 MQTT：IoT 的"群聊协议"

HTTP 的短板：只能客户端发起请求，服务器没法主动推。MQTT 解决它：

- 基于 TCP 的轻量发布/订阅协议（发布者→主题→订阅者，快递站只认"信箱号"不认收件人）
- 报文头最小 2 字节（HTTP 头动辄几百字节），省流量
- 内置 QoS（0 最多一次 / 1 至少一次 / 2 恰好一次）、心跳保活、遗嘱消息

设备 OTA 场景常用 MQTT 接收"升级指令"（服务器推送），再用 HTTP 大文件下载固件——各取所长。
