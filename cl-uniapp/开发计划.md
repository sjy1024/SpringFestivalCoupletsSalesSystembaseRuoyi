我先看一下 cl-uniapp 这个小程序项目的结构和配置（页面、工具目录等），然后结合你已经写好的后端 C 端接口，给你出一份专门针对这个项目的分阶段开发计划。
整体判断
cl-uniapp 其实是腾讯 TDesign 的零售电商小程序模版，功能很全：
首页、商品列表/详情、购物车、下单、订单列表/详情、售后、个人中心等，目前主要用的是 model/ + services/ 里的 mock 数据。
你的目标：把它改造成 连你若依后端的春联小程序。
所以计划的核心就是：“保留页面结构 + 替换数据来源 + 精简不需要的业务”。
一、整体开发思路（先说结论）
按你现在后端进度（已完成 /api/app/goods、/api/app/order 在做），建议：
第一阶段：最小可用版本（MVP，先跑通主链路）
商品：首页/列表/详情 → 你的 /api/app/goods/list、/api/app/goods/{id}
下单：确认订单页 → /api/app/order/create（后端你稍后实现）
订单：订单列表/详情 → /api/app/order/list、/api/app/order/{id}
保留简单“设备ID / 收货电话”方式标识用户（先不做登录）。
第二阶段：清理和定制
去掉暂时用不到的券、活动、复杂售后页面
UI 文案、图片改成“春联 / 对联”风格
加上你订单状态“已收货”等业务按钮。
第三阶段：增强功能（可选）
登录 + 角色区分
AI 聊天下单、定制订单
更复杂的售后流程。
二、基于 cl-uniapp 的具体开发计划（按目录来）
1. 全局配置 & 请求封装（1 天）
目标：建立“统一请求入口”，后面页面只调 services，你在一处改后端地址即可。
具体任务：
在 services/_utils/ 或 utils/ 下新增一个简单的 request.js：
配置 BASE_URL = http://localhost:8080（或你的 Nginx 域名）
封装 wx.request，统一处理：
成功：返回 { code, data, msg }
失败：wx.showToast 提示
调整 services/ 下的接口文件（先从 services/good、services/order 开始）：
把原先读 model/ / mock 的逻辑，改成调用你的若依接口：
商品列表 → 调 /api/app/goods/list
商品详情 → 调 /api/app/goods/{id}
订单列表 → 调 /api/app/order/list
订单详情 → 调 /api/app/order/{orderId}
> 这一步做完，相当于把“数据总开关”打通，后面所有页面都走你后端。
2. 商品主链路（首页 / 列表 / 详情）（1–2 天）
涉及目录：
pages/home/home（首页）
pages/goods/list（商品列表）
pages/goods/details（商品详情）
以及 components/goods-card、goods-list 等。
具体任务：
首页：
首页商品区的数据源改成调用 services/good/fetchGoodsList.js，而这个 service 已经指向 /api/app/goods/list。
可以先简单按“推荐商品”展示一个列表。
商品列表页：
pages/goods/list/index.js 中的列表请求改为：
services/good/fetchGoodsList → /api/app/goods/list
支持简单搜索（可选：把搜索词传给 goodsName 参数）。
商品详情页：
pages/goods/details/index.js 中：
页面 onLoad(options) 里用 options.goodsId 调用 services/good/fetchGood（指向 /api/app/goods/{id}）。
展示字段对齐你 ClGoods：封面、图片数组、描述、价格、库存等。
> 做完这一块，你就可以：在手机上真实看到后台配置的商品，并点进去查看详情。
3. 购物车 & 下单（2 天左右）
这里可以简化，不一定要完全照模版的购物车逻辑。
涉及目录：
pages/cart/index（购物车）
pages/order/order-confirm（确认订单页）
pages/order/pay-result（支付结果页）
services/cart、services/order
简化建议：
购物车：
可以先保留“本地购物车”（存 wx.setStorageSync），不用对接后端购物车表，减少后端改动。
把“加入购物车”按钮改成：
将当前商品（goodsId + 数量）存到本地购物车列表。
购物车页面读取本地购物车，展示列表，勾选后“去结算”跳到 order-confirm。
确认订单页：
在 pages/order/order-confirm/index.js 中：
从本地购物车中取出待结算的商品，计算总价。
填写收货人、电话、地址（可以复用模版中的地址组件）。
点击“提交订单”时，调用你后面要实现的：
POST /api/app/order/create
请求体：{ deviceId/receiverPhone, receiverName, receiverAddress, items: [{ goodsId, quantity }] }
成功后跳转到 pay-result 页面。
支付结果页：
当前模版里是 mock，你可以直接改成：
成功创建订单后，展示“下单成功，订单号 xxx”，提供“查看订单详情”和“返回首页”按钮。
如果你后端实现了 /mockPay 接口，可以在这里模拟支付再改状态。
> 这一块做完，你的主流程就已经闭环：商品 → 购物车 → 提交订单 → 查看支付结果。
4. 我的订单（1 天）
涉及目录：
pages/order/order-list
pages/order/order-detail
services/order/orderList.js、orderDetail.js
具体任务：
order-list：
请求改为调用 /api/app/order/list：
参数：deviceId 或 receiverPhone（与后端保持一致）。
列表展示：订单号、状态、总价、下单时间等。
order-detail：
用订单 ID（或订单号）调用 /api/app/order/{id}。
展示：收货信息、订单状态、商品明细（如果后端暂时没返回明细，可以先只显示主信息）。
> 做完后，用户可以在小程序里看“我的订单”和每一单的详细信息。
5. 用户标识方案（0.5–1 天）
短期内你可以采用简单方案：
方案 A：设备 ID（无登录，最快）
在小程序启动时生成 deviceId（如 Date.now() + 随机数），存 wx.setStorageSync('deviceId')。
前端调用订单相关接口时，都自动带上 deviceId。
后端用 cl_order.device_id 过滤订单列表。
方案 B：收货电话作为“唯一标识”（也行）
下单时必须填收货电话。
查询订单列表时传 receiverPhone，后端按此过滤。
后续你想做“登录 + 分角色”，再切到我们之前文档里写的 AppAuth 方案即可。
6. 清理和定制（1–2 天，按需）
去掉现在暂时用不到的模块：
pages/coupon、pages/promotion、订单售后里过于复杂的页面等。
把文案、图标替换成你的主题：
首页 Banner、商品分类、文案改为“春联 / 对联 / 门贴”等。
style/theme.wxss 可以按你现在的若依春节主题做一套主色。
三、基于你当前进度的时间预估
你后端已具备基础能力（商品 / 订单表 + 管理后台 + 部分 C 端接口），再加上这个现成 TDesign 模版：
打通主链路（阶段 1 + 2 + 3 + 4 + 简单用户标识）：约 4–6 天
清理/美化 + 选做功能：再加 2–3 天
完全在你之前整体 10+ 天的预算之内，而且页面观感很好，适合作答辩展示。
