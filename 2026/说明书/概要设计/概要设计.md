4.1	系统架构设计
4.1.1	总体架构说明
本系统采用前后端分离的三层架构设计，整体分为表现层、业务逻辑层和数据访问层。系统由微信小程序前端、Vue2 管理后台前端与 Spring Boot 后端组成，前后端通过 RESTful API 通信。
系统总体架构从上至下分为以下层次：
（1）**客户端层**：微信小程序面向消费者，提供浏览、购物车、订单、定制与 AI 对话等能力；Vue2 管理后台面向管理员，提供商品、订单、定制与统计等运维能力。两端与后端之间均为无状态的请求—响应式交互。
（2）**接口与鉴权层**：后端在同一应用中划分面向小程序的 `/api/app/*` 与面向管理端的 `/cl/*`、`/system/*` 等路径。小程序侧通过设备 ID 关联业务数据，管理端通过 JWT 等机制完成认证与授权，由 Spring Security 与若依既有机制统一拦截非法访问。
（3）**业务逻辑层**：在单一部署单元内划分商品、订单、购物车、定制、AI 助手等**逻辑模块**（以包与 Service 为界），各模块协作完成下单、库存变更、定制排队与对话记录持久化等流程，而非物理上的多微服务进程。
（4）**数据访问层**：通过 MyBatis 映射 SQL，完成业务实体与关系表之间的读写；对历史订单等场景采用快照字段，降低主数据变更对追溯的影响。
（5）**基础设施层**：MySQL 承担主数据持久化；Redis 可用于 Token、验证码与热点数据缓存；Ollama 提供本地大语言模型推理能力，由后端 AI 服务模块封装调用，与主业务数据库解耦。

4.1.3	架构说明

从部署与职责划分看，**微信小程序**承担 C 端全部交互，负责展示商品与定制选项、维护本地设备标识、调用后端 JSON 接口并渲染页面，本身不持久化核心业务数据。**管理后台**在 PC 浏览器中运行，依赖若依提供的布局与权限菜单，管理员在登录后完成商品上下架、订单与定制单处理、统计查看等操作，所有写操作经鉴权后进入对应业务模块。

**Spring Boot 应用**作为唯一的业务与接口承载进程，对内调度各 Service 与 Mapper，对外暴露 REST 接口。商品、订单、购物车、用户地址、定制排队与 AI 聊天记录等流程均在应用内以模块化方式实现：例如商品模块负责上架校验与扩展属性维护，订单模块负责状态机与库存配合，定制模块与订单模块协同完成定制单生命周期，AI 模块负责组装提示词、调用 Ollama 并写回对话与推荐结果。

**MySQL** 存储商品、订单、明细、购物车、定制、评价与对话日志等关系数据，是保证一致性的权威数据源。**Redis** 在系统中主要服务于登录态、验证码及可选的热点缓存，减轻数据库压力并控制会话有效期。**Ollama** 部署于服务器或同机侧，为自然语言问答与春联相关推荐提供推理能力；后端通过 HTTP 调用其 API，将模型输出与商品检索结果整合后返回小程序。

整体上，该架构在毕设规模下兼顾**实现复杂度可控**与**职责清晰**：前后端分离便于并行开发与联调，三层结构便于对照教材撰写设计说明，本地 AI 与模拟支付则与系统边界说明相呼应。

4.1.4	前后端交互流程
小程序端的交互流程如下：小程序启动时自动生成唯一设备ID并持久化存储，后续所有API请求均携带该设备ID作为用户标识。请求通过统一封装的request工具发送，自动处理若依标准响应格式（{code: 200, data: ..., msg: ...}），并统一处理加载状态和错误提示。
管理后台的交互流程如下：管理员通过账号密码登录，后端验证通过后返回JWT Token，前端将Token存储在本地，后续请求在请求头中携带Token进行身份验证。Token过期后自动跳转到登录页面重新认证。

本系统的核心实体及其关系如下：
（1）商品（Goods）实体：具有商品ID、商品名称、商品类型、价格、库存、封面图片、商品图片、描述、评分、上架状态等属性。商品分为普通商品和需要材质尺寸的定制商品两种类型。
（2）商品扩展（GoodsExtend）实体：具有扩展ID、商品ID、材质、尺寸、纸张类型、印刷类型等属性。与商品实体存在一对一关系，仅定制类型商品拥有扩展信息。
（3）购物车（Cart）实体：具有购物车ID、设备ID、商品ID、数量等属性。设备ID与商品ID的组合具有唯一性约束，同一设备同一商品只有一条购物车记录。
（4）订单（Order）实体：具有订单ID、订单号、设备ID、订单类型、总金额、状态、收货人姓名、收货人电话、收货地址等属性。订单状态包括待支付、已支付、制作中、已完成、已取消五种状态。
（5）订单明细（OrderItem）实体：具有明细ID、订单ID、商品ID、商品名称快照、价格快照、数量等属性。与订单存在多对一关系，一个订单可包含多条明细。
（6）定制订单（CustomOrder）实体：具有定制ID、订单ID、排队号、排队位置、预计完成时间、定制内容、定制状态等属性。与订单存在一对一关系，仅定制类型订单拥有定制订单记录。
（7）商品评价（GoodsEvaluation）实体：具有评价ID、设备ID、商品ID、订单ID、评分、评价内容、评价图片等属性。
（8）AI对话记录（AIChatLog）实体：具有聊天ID、设备ID、用户问题、AI回答、推荐商品列表等属性。
主要实体关系：
商品与商品扩展：一对一关系（仅定制商品有扩展信息）
设备（用户）与购物车：一对多关系（一个设备可有多条购物车记录）

商品与商品评价：一对多关系
设备（用户）与AI对话记录：一对多关系
