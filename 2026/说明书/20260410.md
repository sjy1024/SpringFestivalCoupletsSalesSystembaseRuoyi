# 设计总说明

设计背景

随着传统文化的复兴和人们对节日氛围的重视，春联作为中国传统节日文化的重要组成部分，市场需求逐年增长。然而，传统的春联销售模式存在诸多问题，如：线下店铺覆盖范围有限、定制服务流程繁琐、排队等待时间长、缺乏个性化推荐等。为了解决这些问题，开发一套集线上销售、定制服务、智能推荐于一体的春联售卖系统显得尤为必要。

设计目标与核心功能

本设计旨在开发一套完整的春联售卖系统，包括后台管理系统和微信小程序前端。系统采用前后端分离架构，后端基于Spring Boot和MyBatis实现，前端分为管理后台（Vue2 + ElementUI）和微信小程序（TDesign组件库）。核心功能包括：

商品管理：支持普通春联和定制春联的管理，包括商品信息的增删改查、库存管理等。

订单管理：支持普通订单和定制订单的处理，实现订单状态的流转跟踪。

定制服务：提供春联定制功能，支持用户选择材质、尺寸、印刷方式等定制选项。

排队系统：针对定制订单实现智能排队功能，计算预计完成时间，提高用户体验。

AI对话推荐：集成AI对话功能，根据用户需求推荐合适的春联产品。

购物车管理：支持商品的添加、修改、删除等操作，实现批量结算。

技术亮点

前后端分离架构：采用Spring Boot + Vue2 + 微信小程序的前后端分离架构，提高系统的可维护性和扩展性。

智能排队系统：基于订单数量和处理时间，智能计算定制订单的排队位置和预计完成时间。

AI智能推荐：集成AI对话功能，根据用户需求和历史数据推荐个性化春联产品。

响应式设计：管理后台采用ElementUI实现响应式布局，小程序前端适配不同屏幕尺寸。

数据安全：采用Spring Security实现权限管理，确保系统数据安全。

本文主要内容

本文详细介绍春联售卖系统的设计与实现过程，包括系统需求分析、架构设计、数据库设计、功能模块实现等。全文共分为八章，第一章为系统绪论，介绍项目背景和意义；第二章为相关技术介绍，阐述系统使用的技术栈；第三章为需求分析，详细分析系统的功能需求和非功能需求；第四章为概要设计，描述系统的总体架构和模块划分；第五章为详细设计，详细介绍各模块的实现细节；第六章为系统实现，展示系统的具体实现和界面效果；第七章为系统测试，验证系统的功能和性能；第八章为总结和展望，总结系统的完成情况并提出未来改进方向。

# 系统绪论1.1 背景和意义

春联作为中国传统节日文化的重要载体，承载着人们对新年的美好祝愿和期盼。据统计，每逢春节前后，全国春联市场销售额可达数十亿元，市场规模持续扩大。随着人们生活水平的提高和对传统文化的重视，春联市场需求持续增长。然而，传统的春联销售模式存在以下问题：

（1）销售渠道单一：主要依赖线下实体店，覆盖范围有限，无法满足消费者的便捷购物需求。尤其是在非节日期间，线下门店客流量稀少，经营成本高。

（2）定制服务不便：传统定制春联需要到店咨询、现场沟通，流程繁琐，等待时间长。消费者无法提前了解定制进度，体验较差。

（3）缺乏个性化推荐：消费者难以快速找到符合自己需求的春联产品，尤其是定制需求多样化的情况下，人工推荐效率低下。

（4）订单管理混乱：传统手工记录订单方式容易出错，订单状态不透明，影响用户体验，也增加了商家的管理成本。

基于以上问题，开发一套集线上销售、定制服务、智能推荐于一体的春联售卖系统具有重要意义：

（1）拓展销售渠道：通过微信小程序实现线上销售，依托微信庞大的用户基础，覆盖更广泛的用户群体，突破地域限制。

（2）提升定制服务体验：在线定制功能让用户可以随时随地提交定制需求，智能排队系统实时反馈排队进度，提高服务效率和透明度。

（3）个性化推荐：AI对话功能根据用户需求推荐合适的春联产品，降低用户选择成本，提升用户满意度。

（4）规范化订单管理：系统自动记录和跟踪订单状态，提高管理效率和透明度，减少人工错误。

## 1.2 相关研究

目前，市场上已有一些电商系统和定制服务平台，但针对春联这一特定领域的专业系统还相对较少。相关研究主要集中在以下几个方面：

（1）电商系统研究：淘宝、京东等大型电商平台提供了成熟的商品管理、订单处理和支付功能，为本系统的设计提供了参考。但这类平台通用性强，缺乏针对春联定制的专业服务，无法满足春联行业的特殊需求

（2）定制服务平台研究：部分印刷定制平台提供了定制服务，但缺乏针对春联的专业设计和推荐功能，且用户体验有待提升。

（3）智能推荐系统研究：基于用户行为和偏好的智能推荐技术已经在电商领域广泛应用，协同过滤、内容推荐等算法日趋成熟。但在春联领域，由于数据积累不足，智能推荐的应用还处于起步阶段

（4）排队系统研究：在餐饮、医疗等领域已有成熟的排队管理系统，基于先进先出原则的队列算法能够有效管理服务顺序。将排队系统引入春联定制服务，可以有效解决高峰期订单积压问题。

（5）AI对话技术研究：随着大语言模型技术的快速发展，AI对话系统在电商导购、客服等场景的应用日益广泛。将AI对话技术应用于春联推荐，能够提供更自然、更个性化的购物引导体验。

本系统在借鉴现有研究成果的基础上，针对春联销售的特点，开发了一套集电商、定制、智能推荐于一体的专业系统，弥补了市场空白。

## 1.4 创新点

本系统的创新点主要体现在以下几个方面：

（1）行业针对性：专门针对春联销售和定制服务设计，在商品分类、定制选项、推荐逻辑等方面充分考虑春联行业的特殊需求，而非通用电商系统的简单套用。

（2）智能排队系统：基于订单数量和历史处理时间，智能计算定制订单的排队位置和预计完成时间，并向用户实时展示排队进度，有效缓解用户等待焦虑，提高服务效率

（4）免登录设计：采用设备ID标识用户，无需注册登录即可完成购物全流程，降低用户使用门槛，符合微信小程序轻量化的使用场景。

（5）多端适配：同时支持PC端管理后台和微信小程序前端，管理员可通过后台高效管理商品和订单，用户可通过小程序便捷购物，满足不同角色的使用需求。

# 相关技术介绍

## 2.1 后端技术

### 2.1.1 Spring Boot

Spring Boot是由Pivotal团队开发的基于Spring框架的快速开发脚手架，它简化了Spring应用的初始搭建和开发过程。Spring Boot的主要特点包括：

（1）自动配置：根据项目依赖自动配置应用环境，减少配置文件的编写，开发者可以专注于业务逻辑的实现。

（2）嵌入式容器：内置Tomcat、Jetty等Web容器，无需单独部署，可直接打包为可执行的JAR文件运行。

（3）Starter依赖：提供一系列Starter依赖，将相关依赖统一管理，简化Maven/Gradle的依赖配置。

（4）生产就绪：提供健康检查、指标监控、外部化配置等生产环境所需的功能，便于运维管理。

本系统基于若依（RuoYi）框架进行开发，若依框架是一套基于Spring Boot构建的快速开发平台，内置了权限管理、代码生成、系统监控等通用功能，大幅提升了开发效率。在本系统中，Spring Boot作为后端核心框架，负责处理业务逻辑、数据库操作和API接口的统一管理。

### 2.1.2 MyBatis

MyBatis是一款优秀的持久层框架，它支持定制化SQL、存储过程以及高级映射。MyBatis的主要特点包括：

（1）灵活的SQL编写：支持手写SQL，开发者可以精确控制SQL语句，便于针对特定场景进行查询优化。

（2）动态SQL：通过XML配置文件或注解实现动态SQL，可根据不同的查询条件动态拼接SQL语句，适应复杂的查询场景。

（3）结果映射：支持复杂的结果集映射，包括一对一、一对多等关联关系的自动映射，减少手动处理结果集的工作量。

（4）缓存机制：提供一级缓存（SqlSession级别）和二级缓存（Mapper级别），有效减少数据库访问次数，提高查询性能。

在本系统中，MyBatis负责数据库操作层的实现，通过XML映射文件定义SQL语句，实现商品、订单、购物车等数据的增删改查功能。

### 2.1.3 MySQL

MySQL是一款开源的关系型数据库管理系统，由Oracle公司维护，以其可靠性、稳定性和高性能而闻名。MySQL的主要特点包括：

（1）开源免费：采用GPL协议，社区版可自由使用，降低了系统的开发和运维成本。

（2）高性能：InnoDB存储引擎提供行级锁定和外键约束，支持高并发读写操作，满足电商系统的性能需求。

（3）可靠性：支持ACID事务、二进制日志和备份恢复机制，确保数据的一致性和安全性。

（4）扩展性：支持主从复制、读写分离等扩展方案，可根据业务增长灵活扩展数据库集群。

在本系统中，MySQL作为主要数据存储引擎，存储商品、订单、购物车、定制订单、AI对话记录等业务数据。

## 4.1 系统架构设计

### 4.1.1 总体架构说明

本系统采用**前后端分离**与**经典三层结构**（表现层、业务逻辑层、数据访问层）相结合的方案。表现层由微信小程序与管理后台（Vue2）构成，二者均通过 HTTP/HTTPS 调用同一 Spring Boot 后端暴露的 RESTful 接口；业务逻辑层在服务端以 Controller、Service、Mapper 分层组织，封装春联售卖、定制排队、模拟支付与 AI 对话等业务规则；数据访问层基于 MyBatis 访问 MySQL，并可结合 Redis 做会话与热点数据支撑。

系统自上而下可概括为以下层次。

（1）**客户端层**：微信小程序面向消费者，提供浏览、购物车、订单、定制与 AI 对话等能力；Vue2 管理后台面向管理员，提供商品、订单、定制与统计等运维能力。两端与后端之间均为无状态的请求—响应式交互。

（2）**接口与鉴权层**：后端在同一应用中划分面向小程序的 `/api/app/*` 接口与面向管理端的 `/cl/*`、`/system/*` 等路径。小程序侧通过设备 ID 关联业务数据，管理端通过 JWT 等机制完成认证与授权，由 Spring Security 与若依既有机制统一拦截非法访问。

（3）**业务逻辑层**：在单一部署单元内划分商品、订单、购物车、定制、AI 助手等**逻辑模块**（以包与 Service 为界），各模块协作完成下单、库存变更、定制排队与对话记录持久化等流程，而非物理上的多微服务进程。

（4）**数据访问层**：通过 MyBatis 映射 SQL，完成业务实体与关系表之间的读写；对历史订单等场景采用快照字段，降低主数据变更对追溯的影响。

（5）**基础设施层**：MySQL 承担主数据持久化；Redis 可用于 Token、验证码与热点数据缓存；Ollama 提供本地大语言模型推理能力，由后端 AI 服务模块封装调用，与主业务数据库解耦。

### 4.1.3 架构说明

从部署与职责划分看，**微信小程序**承担 C 端全部交互，负责展示商品与定制选项、维护本地设备标识、调用后端 JSON 接口并渲染页面，本身不持久化核心业务数据。**管理后台**在 PC 浏览器中运行，依赖若依提供的布局与权限菜单，管理员在登录后完成商品上下架、订单与定制单处理、统计查看等操作，所有写操作经鉴权后进入对应业务服务。

**Spring Boot 应用**作为唯一的业务与接口承载进程，对内调度各 Service 与 Mapper，对外暴露 REST 接口。商品、订单、购物车、用户地址、定制排队与 AI 聊天记录等流程均在应用内以模块化方式实现：例如商品模块负责上架校验与扩展属性维护，订单模块负责状态机与库存配合，定制模块与订单模块协同完成定制单生命周期，AI 模块负责组装提示词、调用 Ollama 并写回对话与推荐结果。

**MySQL** 存储商品、订单、明细、购物车、定制、评价与对话日志等关系数据，是保证一致性的权威数据源。**Redis** 在系统中主要服务于登录态、验证码及可选的热点缓存，减轻数据库压力并控制会话有效期。**Ollama** 部署于服务器或同机侧，为自然语言问答与春联生成提供推理能力；后端通过 HTTP 调用其 API，将模型输出与商品检索结果整合后返回小程序。

整体上，该架构在毕设规模下兼顾**实现复杂度可控**与**职责清晰**：前后端分离便于并行开发与联调，三层结构便于对照教材撰写设计说明，本地 AI 与模拟支付则明确界定系统边界（见第 3.6 节）。

### 4.1.4 前后端交互流程

小程序端的交互流程如下：小程序启动时自动生成唯一设备 ID 并持久化存储，后续所有 API 请求均携带该设备 ID 作为用户标识。请求通过统一封装的 request 工具发送，自动处理若依标准响应格式（`{code: 200, data: ..., msg: ...}`），并统一处理加载状态与错误提示。

管理后台的交互流程如下：管理员通过账号密码登录，后端验证通过后返回 JWT Token，前端将 Token 存储在本地，后续请求在请求头中携带 Token 进行身份验证。Token 过期后自动跳转到登录页面重新认证。

数据库e-r图

本系统的核心实体及其关系如下：

主要实体关系：

商品与商品扩展：一对一关系（仅定制商品有扩展信息）

设备（用户）与购物车：一对多关系（一个设备可有多条购物车记录）

购物车与商品：多对一关系

## 5.1 商品管理模块

### 5.1.1 模块概述

商品管理模块是系统的核心基础模块，负责春联商品信息的全生命周期管理。该模块向上为小程序端和管理后台提供商品数据服务，向下与数据库进行持久化交互。模块采用标准三层架构（Controller → Service → Mapper），各层通过接口解耦，职责边界清晰。

### 5.1.3 业务流程设计

商品列表查询流程如下：

（1）小程序发起GET请求，携带可选查询参数（goodsName、goodsType）。

（2）AppGoodsController接收请求，构建ClGoods查询对象，强制设置status="0"，确保只返回上架商品。

（3）调用IClGoodsService.selectClGoodsList()执行业务查询，MyBatis根据传入条件动态拼接WHERE子句。

（4）查询结果逐层返回，Controller封装为AjaxResult标准格式响应给小程序。

（5）小程序端request工具解析响应，调用toAbsoluteUrl()将图片相对路径转换为绝对URL后渲染页面。

商品新增流程如下：

（1）管理员填写商品信息，提交POST请求至/cl/goods。

（2）系统校验商品名称非空、价格非负、库存非负等基本合法性，不合法请求在进入业务层前被拦截。

（3）向cl_goods表插入商品主记录，获取数据库自增的goodsId。

（4）若goodsType=1（定制商品），在同一事务中同步向cl_goods_extend表插入扩展信息记录。

（5）返回操作结果，管理后台刷新商品列表。

## 5.2 订单管理模块

### 5.2.1 模块概述

订单管理模块负责处理用户订单的全生命周期，包括订单创建、支付确认、状态流转和信息查询等功能。模块采用状态机模式管理订单状态，通过数据库事务保证订单数据的一致性。

订单分为两种类型：普通订单（orderType=0）和定制订单（orderType=1）。普通订单创建后直接进入待支付状态；定制订单创建后除进入待支付状态外，还会同步创建定制订单记录并加入排队系统。订单状态共5种，状态编码及流转规则如下表所示：

| **状态编码** | **状态名称** | **可流转至** | **触发条件** |
| --- | --- | --- | --- |
| 0   | 待支付 | 1（已支付）、4（已取消） | 用户完成支付 / 用户主动取消 |
| 1   | 已支付 | 2（制作中）、4（已取消） | 管理员接单 / 管理员取消 |
| 2   | 制作中 | 3（已完成）、4（已取消） | 管理员完成制作 / 管理员取消 |
| 3   | 已完成 | —   | 终态，不可再流转 |
| 4   | 已取消 | —   | 终态，不可再流转 |

## 5.3 定制服务模块

### 5.3.1 模块概述

定制服务模块是本系统的特色功能模块，为用户提供春联个性化定制服务。模块包含三个核心子功能：定制选项管理、智能排队系统和预计时间计算。该模块与订单管理模块紧密协作，定制订单的创建依托订单管理模块的事务机制保证数据一致性。

### 5.3.3 智能排队系统设计

排队系统采用先进先出（FIFO）原则，核心算法如下。

排队位置计算：新订单的排队位置等于当前处于"待接单"（status=0）或"制作中"（status=1）状态的定制订单总数加1，即：排队位置 = COUNT(status IN (0, 1)) + 1。

预计完成时间计算：预计完成时间 = 当前时间 + 排队位置 × 平均处理时长。平均处理时长默认设定为30分钟/单，可由管理员在系统参数中动态调整。

排队号生成规则：排队号格式为Q + yyyyMMdd（8位日期）+ 3位序号，例如Q20260201001。序号在每日内从001开始递增，跨日后重置。

排队位置动态更新机制：当管理员将某定制订单状态更新为"已完成"（status=2）时，系统自动触发以下更新逻辑：

（1）查询所有排队位置大于当前完成订单排队位置的待处理定制订单。

（2）将上述订单的queue_position字段值减1。

（3）根据新的排队位置重新计算estimated_time字段。

（4）上述操作在同一数据库事务中执行，保证排队数据的一致性。

### 5.3.4 业务流程设计

定制订单提交流程如下：

（1）用户在小程序定制页面选择定制选项（材质、尺寸、印刷方式），输入定制文字内容，填写收货信息，点击提交。

（2）小程序将定制选项序列化为JSON格式，连同收货信息一起发送POST请求至/api/app/custom/create。

（3）AppCustomController接收请求，调用定制服务创建逻辑。

（4）系统在数据库事务中依次执行：创建订单主记录（orderType=1）；创建订单明细记录；计算排队位置和预计完成时间；生成排队号；创建定制订单记录。

（5）事务提交成功后，返回orderId、排队号（queueNo）、排队位置（queuePosition）和预计完成时间（estimatedTime）。

（6）小程序展示排队信息卡片，告知用户当前排队状态。

### 5.4.1 模块概述

### 6.1.2 商品管理模块实现

商品管理模块后端实现遵循标准三层架构，各层实现要点如下。

（1）控制层（AppGoodsController / ClGoodsController）

小程序端控制器（AppGoodsController）标注@Anonymous注解，允许无Token访问，对外提供两个只读接口：商品列表接口固定追加status="0"查询条件，确保只返回上架商品；商品详情接口在商品不存在时返回业务错误码而非抛出异常，保证接口健壮性。

（2）业务层（ClGoodsServiceImpl）

业务层实现IClGoodsService接口，核心逻辑如下：商品新增时先向cl_goods表插入主记录，获取自增goodsId，若goodsType=1则在同一事务中向cl_goods_extend表插入扩展记录；商品修改时更新主记录后，通过extendId是否存在决定执行INSERT还是UPDATE来同步处理扩展记录；商品删除时批量删除主记录的同时同步删除对应扩展记录，防止孤立数据残留。

（3）数据访问层（ClGoodsMapper）

Mapper接口对应的XML映射文件中，selectClGoodsList方法使用MyBatis动态SQL，通过&lt;if&gt;标签按需拼接WHERE子句，支持以下查询条件的任意组合：

| **查询条件** | **SQL片段** | **说明** |
| --- | --- | --- |
| goodsName不为空 | AND goods_name LIKE #{goodsName} | 商品名称模糊查询 |
| goodsType不为空 | AND goods_type = #{goodsType} | 商品类型精确匹配 |
| status不为空 | AND status = #{status} | 上架状态精确匹配 |

查询结果按sort_order升序、create_time降序排列，保证展示顺序的稳定性。

### 6.1.4 定制服务模块实现

（1）定制订单创建

定制订单的创建在普通订单创建流程基础上，在同一事务中额外执行以下步骤：

第一步，查询排队总数：统计当前cl_custom_order表中status为"0"（待接单）或"1"（制作中）的记录数量，作为当前排队总数。

第二步，计算排队位置：queuePosition = 排队总数 + 1。

第三步，计算预计完成时间：estimatedTime = 当前时间 + queuePosition × 30分钟。

第四步，生成排队号：格式为Q + yyyyMMdd + 当日序号（3位，不足补零）。

第五步，向cl_custom_order表插入定制订单记录，status初始值为"0"（待接单）。

（2）排队位置动态更新

管理员通过CS-04接口将定制订单状态更新为"已完成"（status=2）时，系统在同一事务中执行级联更新：将cl_custom_order表中所有排队位置大于当前完成订单排队位置、且状态仍为待处理的记录，其queue_position字段值减1，同时根据新的排队位置重新计算estimated_time字段。该操作确保已完成订单之后的所有待处理订单排队位置自动前移，预计完成时间同步更新，用户在小程序端刷新后即可看到最新排队状态。

（3）定制内容存储

定制内容以JSON字符串形式存储在custom_content字段中，后端使用FastJSON进行序列化和反序列化。管理后台查看定制详情时，系统将JSON字符串解析为可读的键值对展示给管理员，包括材质、尺寸、印刷方式、定制文字内容和特殊要求等信息。

### 6.1.5 AI对话模块实现

（1）组件协作关系

AI对话模块由三个组件协作完成：

| **组件** | **职责** |
| --- | --- |
| AppAIController | 接收小程序请求，参数校验，调用业务层，返回响应 |
| AdminAssistantService | 核心业务逻辑：构建提示词、调用AI、解析结果、保存记录 |
| OllamaService | AI服务适配层：封装与本地Ollama HTTP API的通信细节 |

（2）系统提示词构建策略

每次对话前，AdminAssistantService从数据库查询所有上架商品，将商品信息格式化为结构化文本注入系统提示词。提示词包含角色定义（"你是一个专业的春联销售助手"）、当前可售商品列表（含商品ID、名称、类型、价格）和推荐约束（"只能推荐列表中存在的商品，不得虚构商品信息"）。该策略将商品数据与AI能力结合，使推荐结果始终基于真实库存。

（3）推荐商品提取

AI回答生成后，系统对回答文本进行后处理：遍历商品列表，对每个商品名称执行字符串包含匹配，将命中的商品加入推荐列表。该方法实现简单可靠，适合商品数量有限的场景。

（4）OllamaService实现

OllamaService通过Spring的RestTemplate向本地Ollama服务（默认地址http://localhost:11434/api/chat）发送POST请求，请求体包含模型名称（model）、消息列表（messages，含system角色和user角色）、流式开关（stream: false）。响应解析后提取message.content字段作为AI回答文本返回。

### 6.2.3 设备ID管理实现

系统采用设备ID（deviceId）代替用户账号标识用户，实现免注册、免登录的购物体验。设备ID的生命周期管理由utils/deviceId.js负责，具体实现逻辑如下：

（1）小程序启动时，app.js的onLaunch生命周期函数调用getDeviceId()方法。

（2）getDeviceId()首先尝试从本地持久化存储（wx.getStorageSync('deviceId')）读取已有的设备ID。

（3）若本地存储中存在有效的设备ID，直接返回该值，保证同一设备的ID不变。

（4）若本地存储中不存在设备ID（首次启动或存储被清除），则按照"device_时间戳_随机字符串"的格式生成新的设备ID。

（5）将新生成的设备ID通过wx.setStorageSync持久化存储到本地，并挂载到app.globalData.deviceId，供所有页面和服务层在发起API请求时使用。

# 8.总结和展望

## 8.1 系统完成情况

本系统历经需求分析、架构设计、数据库设计、编码实现和测试验证等阶段，已完成以下功能模块的开发：

（1）商品管理：实现了商品信息的增删改查、图片上传、上下架管理、库存管理等功能，支持普通商品和定制商品两种类型，定制商品可关联材质、尺寸等扩展信息。

（2）订单管理：实现了普通订单和定制订单的创建、查询、状态流转等功能，订单状态覆盖待支付、已支付、制作中、已完成、已取消五个阶段，支持管理员手动更新订单状态。

（3）定制服务：实现了春联定制功能，用户可在线选择材质、尺寸、印刷方式等定制选项，系统自动计算定制价格；智能排队系统根据当前排队情况计算排队位置和预计完成时间，并在管理员处理订单时动态更新排队信息。

（4）AI对话推荐：集成本地Ollama大语言模型服务，实现了基于自然语言的商品推荐功能，系统将商品数据库信息注入提示词，引导AI进行准确的商品推荐，并将对话记录持久化存储。

（5）购物车管理：实现了购物车商品的添加、数量修改、删除、清空等操作，支持多商品批量结算，同一设备同一商品自动合并数量。

（6）用户地址管理：实现了收货地址的增删改查功能，支持设置默认地址，订单创建时可快速选择已保存的地址。

（7）管理后台：基于若依框架实现了完整的后台管理系统，包含商品管理、订单管理、定制管理等核心功能模块，以及若依框架原有的系统管理、权限管理、日志管理等基础功能。

## 8.2 系统优缺点

### 8.2.1 系统优点

（1）前后端分离架构：采用Spring Boot + Vue2 + 微信小程序的前后端分离架构，各端独立开发和部署，接口契约清晰，系统的可维护性和扩展性良好。

（2）免登录设计：采用设备ID标识用户，无需注册登录即可完成购物全流程，大幅降低了用户使用门槛，符合微信小程序轻量化的使用场景特点。

（3）智能排队系统：针对定制订单的特殊需求，设计并实现了智能排队系统，能够实时计算排队位置和预计完成时间，并在订单状态变更时动态更新，有效提升了定制服务的透明度和用户体验。

（4）AI智能推荐：将大语言模型技术应用于春联推荐场景，通过将商品数据注入提示词的方式，实现了基于真实商品库的个性化推荐，为用户提供了更自然、更智能的购物引导体验。

（5）数据安全保障：采用Spring Security实现基于角色的权限控制，JWT Token实现无状态身份认证，MyBatis预编译语句防止SQL注入，多层安全机制共同保障系统数据安全。

（6）订单数据快照：订单明细表存储商品名称和价格的快照，确保历史订单记录不受商品信息变更的影响，保证了订单数据的历史准确性。

### 8.2.2 系统缺点

（1）AI模型依赖本地部署：当前AI对话功能依赖本地部署的Ollama服务，对服务器硬件配置要求较高，且模型推理速度受硬件性能影响较大，在高并发场景下响应延迟可能较明显。

（2）支付功能为模拟实现：当前支付功能采用模拟支付方式，未接入真实的微信支付接口，无法在生产环境中实际收款，需要在正式上线前完成真实支付接口的对接。

（3）物流跟踪功能缺失：系统目前未实现物流跟踪功能，用户无法在小程序内查看订单的物流状态，需要通过其他渠道了解配送进度，影响用户体验的完整性。

（4）设备ID方案的局限性：使用设备ID标识用户虽然降低了使用门槛，但也带来了数据隔离问题——同一用户更换设备后无法查看历史订单，且设备ID在某些情况下可能发生变化，导致数据丢失风险。

（5）缺乏营销功能：系统目前未实现优惠券、满减活动、积分等营销功能，在促进用户转化和提升复购率方面存在不足。

## 8.3 未来改进方向

（1）接入真实支付接口：对接微信支付API，实现完整的在线支付流程，包括支付下单、支付回调、退款处理等功能，使系统具备真实的商业运营能力。

（2）升级AI服务方案：考虑接入云端大语言模型API（如通义千问、文心一言等），降低对本地硬件的依赖，提升AI响应速度和稳定性；同时优化推荐算法，结合用户历史行为数据提供更精准的个性化推荐。

（3）引入用户账号体系：在保留设备ID免登录方案的基础上，增加可选的微信授权登录功能，允许用户绑定微信账号，实现跨设备的订单数据同步和更完善的用户画像。

（4）添加物流跟踪功能：接入第三方物流查询API（如快递100、快递鸟等），实现订单物流状态的实时查询和推送通知，提升用户的购后体验。

（5）完善营销功能体系：开发优惠券系统（满减券、折扣券等）、限时促销活动、积分奖励等营销功能，提高用户转化率和复购率，增强系统的商业价值。

（6）增强数据统计分析：在现有基础上扩展数据统计功能，增加商品销量趋势分析、用户行为分析、AI推荐效果分析等维度，为商家的运营决策提供更有价值的数据支撑。

（7）优化系统性能：引入Redis缓存热点商品数据，减少数据库查询压力；对商品图片进行CDN加速，提升图片加载速度；对数据库关键查询字段建立合理索引，进一步提升系统响应性能。

（8）完善售后服务流程：完善退款申请、售后处理等流程，提升用户的购物保障体验。

## 8.4 总结

本系统以春联售卖为核心业务场景，设计并实现了一套完整的线上销售与定制服务平台。系统采用Spring Boot + MyBatis + MySQL的后端技术栈，结合Vue2管理后台和微信小程序前端，构建了前后端分离的现代化应用架构。

在功能实现上，系统不仅覆盖了电商系统的基础功能（商品管理、购物车、订单管理），还针对春联行业的特殊需求，创新性地设计了智能排队系统和AI对话推荐功能，有效解决了传统春联销售模式中定制服务效率低、个性化推荐缺失等痛点问题。

通过系统测试验证，系统各项功能运行正常，性能指标满足设计要求，安全防护机制有效。系统的成功开发，为春联行业的数字化转型提供了一套可参考的解决方案，对传统文化产品的线上销售和定制服务具有一定的实践意义和推广价值。
